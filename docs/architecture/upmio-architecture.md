## 1. Purpose

This document explains the UPMIO layers used by the ClickHouse project and separates Kubernetes-native capabilities from UPMIO capabilities.

## 2. Layered Model

```text
[Product Layer]
ClickHouse Manager API / UI
  - user requests
  - validation
  - resource generation
  - status aggregation
  - healthcheck and diagnostics

[UPMIO API Layer]
Project / UnitSet / Unit / GrpcCall
MysqlReplication / MysqlGroupReplication / ProxysqlSync / other compose CRDs

[UPMIO Controller Layer]
unit-operator
compose-operator

[Package Layer]
upm-packages
  - charts
  - images
  - config templates
  - startup scripts
  - unit-agent integration

[Kubernetes Native Layer]
Namespace / ServiceAccount / Role / RoleBinding
ConfigMap / Secret
Pod / PVC / Service / Endpoint

[Database Runtime Layer]
ClickHouse Server
ClickHouse Keeper
unit-agent
```

## 3. Kubernetes-native vs UPMIO Objects

| Object | Provider | Role |
|---|---|---|
| Pod | Kubernetes | Runs containers |
| PVC / PV | Kubernetes | Persistent storage |
| Service / Endpoint | Kubernetes | Stable network access |
| ConfigMap | Kubernetes | Non-secret configuration |
| Secret | Kubernetes | Credentials and sensitive data |
| Namespace / RBAC | Kubernetes | Isolation and permissions |
| Project | UPMIO | Prepares namespace-level UPMIO prerequisites |
| UnitSet | UPMIO | Instance group abstraction |
| Unit | UPMIO | Single instance abstraction |
| GrpcCall | UPMIO | One-time operation task; future for ClickHouse |
| MysqlReplication / ProxysqlSync | UPMIO compose | Topology management for existing databases |
| PodMonitor | Prometheus Operator CRD | Monitoring discovery resource |

## 4. ClickHouse Mapping

| ClickHouse Concept | UPMIO Mapping | Notes |
|---|---|---|
| ClickHouse Server process | `Unit` generated by `UnitSet(type=clickhouse)` | One Unit maps to one instance/pod |
| ClickHouse Server group | `UnitSet(type=clickhouse)` | MVP: 1 shard x 2 replicas |
| ClickHouse Keeper process | `Unit` generated by `UnitSet(type=clickhouse-keeper)` | One Unit maps to one Keeper node |
| Keeper ensemble | `UnitSet(type=clickhouse-keeper)` | MVP: 3 nodes |
| Cluster grouping | labels and manager model | No public first-class ServiceGroup CRD found |
| Day2 task | `GrpcCall` in future | Current runtime image rejects `type=clickhouse` |

## 5. Control Flow

```text
User / UI / API Client
        |
        v
ClickHouse Manager API
        |
        +--> create/update Project
        +--> create/update Keeper UnitSet
        +--> create/update ClickHouse UnitSet
        +--> read UnitSet / Unit / Pod / PVC / Service status
        +--> run SQL healthcheck against ClickHouse
        +--> query Prometheus API
        |
        v
UPMIO unit-operator reconciles resources
        |
        v
Kubernetes creates Pods, PVCs, Services, ConfigMaps, Secrets
        |
        v
ClickHouse Server and Keeper run inside Kubernetes
```

## 6. Boundary Rules

- Manager must not reimplement Unit/UnitSet reconciliation.
- Manager should not directly create raw Pods/PVCs/Services as the product path.
- Package templates provide database-specific configuration and images.
- UPMIO operators own runtime lifecycle.
- Manager owns product workflow, validation, aggregation, healthcheck, and presentation.

## 7. Future Topology Direction

MVP does not add a ClickHouse compose CRD.

Future productization may add a ClickHouse-specific topology CRD if package templates plus manager orchestration cannot safely manage multi-shard lifecycle.
